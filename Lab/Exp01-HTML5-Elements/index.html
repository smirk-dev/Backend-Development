§ 01

What this page is

The brief was to build a web page using every HTML5 element I could. The tempting version of that is a wall of tags with no meaning attached, so I wrote something I would actually keep: notes from the first backend lab, marked up with the element that fits each piece of content rather than a <div> for everything.

Semantic HTML is the idea behind that choice — a tag should say what the content is, not how it should look. A screen reader can jump between <section> landmarks; it cannot do anything useful with a styled <div>. The same reasoning shows up on the server side, where an API response is only as useful as the structure it carries.

Everything here is local. No CDN, no placeholder image service, no font download. Pull the Wi-Fi and the page still renders exactly the same.

Use the element that best matches the meaning of the content, not the one that looks closest to what you want.

Paraphrased from the HTML Living Standard

A short version of the rule my instructor kept repeating: if you are reaching for a div, you have probably not read the spec yet.

Three kinds of list, three different jobs

Unordered — things with no sequence

    • PostgreSQL

Ordered — where the sequence is the point

  1. Browser opens a TCP connection
  2. Request line and headers go out
  3. Server routes the path to a handler
  4. Handler talks to the database
  5. Response is written back down the same connection

Continuing the same list after a break, using start:

  1. Connection is reused or closed
  2. Browser paints whatever it got

Description — term and meaning

Middleware
A function that sits between the request and the handler and can end the request early.
ORM
A layer that maps rows to objects so you stop writing the same SELECT forty times.
Idempotent
Running it twice leaves the same state as running it once. PUT should be; POST usually is not.
